3. Layered Architecture

▾

Each layer's responsibility and what it must / must not do.

LayerResponsibilityOwnsMust NOT do
PresentationUI rendering, user input, optimistic stateComponents, screens, hooksDirect DB access, business rules
Transport / APIHTTP / RPC handlers, validation, auth checkControllers, route handlers, DTOsBusiness logic, persistence calls
Service / DomainBusiness logic, orchestration, state transitionsServices, use-cases, domain modelsHTTP concerns, raw SQL
Repository / DataPersistence, queries, schema mappingRepositories, ORM, migrationsBusiness decisions, response shaping
IntegrationExternal services (payment gateways, SMS, push)Adapters, webhook handlersDomain logic, data persistence

Boundary rules

  • UI never imports from data layer directly. Always goes through transport.
  • Data layer never depends on UI modules.
  • Services do not perform transport concerns (HTTP response shaping).
  • API handlers are thin — delegate domain logic to services.

4. Data Flow

▾

How a request moves through the system from entry to exit.

Read flow (example)

  1. Client requests GET /api/v1/{{resource}}
  2. API gateway validates auth token → attaches actor_id to context
  3. Route handler parses query params, calls resourceService.list(actor, filters)
  4. Service applies authorization rules, calls resourceRepository.find(filters)
  5. Repository runs the query, returns mapped domain objects
  6. Service may enrich (join cached data, apply derived fields) and returns DTO
  7. Route handler shapes response: { data, meta } envelope, sets cache headers
  8. Client renders

Write flow (example)

  1. Client submits POST /api/v1/{{resource}} with body
  2. API validates body against the canonical schema (Zod / class-validator)
  3. Route handler invokes resourceService.create(actor, dto)
  4. Service runs business rules, persists via repository, emits domain event
  5. Event listeners (notification, audit, analytics) react asynchronously
  6. Route handler returns 201 Created with the new resource and Location header

5. Module Boundaries & Contracts

▾

How services talk to each other. Every cross-service call is a contract.

FromToMechanismContract
{{SERVICE_A}}{{SERVICE_B}}{{REST | event | direct call}}{{endpoint or event name + payload shape}}
{{SERVICE_A}}{{SERVICE_B}}{{...}}{{...}}

Contract rules

  • Every cross-service event has a versioned payload schema.
  • Producers do not know who consumes their events.
  • Consumers must be idempotent — duplicate events MUST NOT cause duplicate side effects.
  • Breaking contract changes require a new version, not a mutation of the old one.

8.4 Indexes Strategy

Index nameTableColumnsQuery pattern
{{idx_name}}{{table}}{{col_a, col_b}}{{e.g. "list by owner, ordered by created_at"}}

Rules of thumb

  • Index every foreign key.
  • Index every column used in WHERE with high selectivity.
  • Composite index when the query filters on multiple columns in the same order.
  • Avoid over-indexing — every index slows writes.

9.4 Security & Secrets

Secret management policy

Never commit secrets to the repo. Use the host's secret store (Vercel env, Railway secrets, AWS Secrets Manager, GitHub Actions secrets). Document variable names only.
