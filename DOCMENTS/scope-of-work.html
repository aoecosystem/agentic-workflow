How to Use This Template — AI Adjustment Guide

▾

This template is the universal foundation of any AO Ecosystem SoW. AI agents and humans should follow these rules when adjusting it for a specific project.

1. What is Universal vs. Project-Specific

2. Adjustment Workflow

  • Read the project brief from the client
  • Replace cover placeholders: {{PROJECT_NAME}}, {{VERSION}}, etc.
  • Adjust Phase 1 — fill problem, solution, application type, commercialization model
  • Define custom roles in addition to default 3 (USER, ADMIN, SUPER_ADMIN)
  • Add new services S7+ for project domain — keep S1-S6 universal
  • For each new service: define modules, features, system behaviors with new IDs
  • Add corresponding schemas to Phase 3 with indexes
  • Add API endpoints to Phase 4
  • Add events to Phase 5 catalog
  • Add domain-specific libraries to Phase 6 (e.g. Yandex Maps for booking, Mux for video)
  • Adjust Phase 7 role-platform matrix and branding tokens
  • Adjust Phase 8 module implementation order based on new dependencies
  • Adjust Phase 9 folder structures — add new modules to backend and frontend
  • Customize Phase 10 risks, assumptions, and out-of-scope to project context

3. Naming Conventions to Follow

  • Service IDs: S1, S2, ..., S11 — assign sequentially, do not skip numbers
  • Service codes: short uppercase, e.g. IDENT, NOTIF, MSG, AUDIT, ANL, PAY, then domain codes
  • Module IDs format: <code>[Px.Sy.MOD]</code> where x = phase, y = service number, MOD = module short code
  • Feature IDs format: <code>SERVICE-MODULE-NN</code> where NN is two-digit number, e.g. <code>IDENT-REG-01</code>
  • System Behavior IDs: <code>SERVICE-MODULE-S0N</code>, e.g. <code>IDENT-REG-S03</code>
  • Event names: <code>{service}.{entity}.{action}</code>, e.g. <code>identity.user.registered</code>
  • Database tables: snake_case plural, e.g. <code>users</code>, <code>booking_holds</code>
  • API paths: kebab-case, e.g. <code>/users/me/saved-searches</code>

4. AI Agent Instructions

  • When adjusting: read entire template first, then modify
  • Never delete universal sections — extend them
  • Always preserve ID conventions when adding new modules
  • Cross-reference: every Feature ID must map to an API endpoint and one or more System Behaviors
  • Cross-reference: every System Behavior must align with database schema and event catalog
  • Generate placeholder values like <code>{{PROJECT_NAME}}</code> for any field that varies per project
  • Output the adjusted SoW as a new HTML file (do not modify this template)

Glossary &amp; ID Conventions

▾

Phase ID Format

[Px.Sy.MOD]
 │   │   └── Module short code (e.g. REG, LOG, PROF)
 │   └────── Service number (1, 2, 3, ...)
 └────────── Phase number (1-10)

Example: [P2.S1.REG] = Phase 2, Service 1 (Identity), Module REG (Registration)

Feature ID Format

SERVICE-MODULE-NN

  SERVICE = Service short code uppercase (IDENT, PAY, BOOK, etc.)
  MODULE  = Module short code uppercase (REG, LOG, PROF, etc.)
  NN      = Two-digit feature number, sequential

Examples:
  IDENT-REG-01    First user feature in Identity → Registration
  PAY-TXN-04      Fourth user feature in Payment → Transactions

System Behavior ID Format

SERVICE-MODULE-SNN

  S = Letter prefix indicating "System behavior"
  NN = Two-digit number

Examples:
  IDENT-REG-S03   Third system behavior in Identity → Registration
  PAY-TXN-S08     Eighth system behavior in Payment → Transactions

Event Name Format

{service}.{entity}.{action}

  service = lowercase service domain
  entity  = primary noun
  action  = past-tense verb

Examples:
  identity.user.registered
  payment.transaction.completed
  booking.confirmed

Index Strategy — Rules of Thumb

  • Always index foreign keys
  • Always unique-index columns used for lookup (email, slug, token)
  • Add partial indexes for soft-delete columns: <code>WHERE deleted_at IS NULL</code>
  • Add composite indexes for common WHERE + ORDER BY combinations
  • Index columns used in filters with high cardinality (status, type)
  • Avoid over-indexing — every index slows down INSERT/UPDATE
  • Use BTREE for equality/range, GIN for JSONB and full-text search
  • Re-evaluate after 30 days in production based on slow-query log

Consumer Rules

  • Listeners must be idempotent

9.6 CI/CD Rules &amp; Conventions

  • Every push to <code>develop</code> or <code>main</code> triggers CI
  • PRs from <code>feature/*</code> or <code>fix/*</code> must pass all CI before merge
  • Lint, type-check, unit tests run on every push
  • E2E tests run only on PR (faster main loop)
  • Code coverage must not drop below 70% (backend) / 50% (frontend)
  • Security scan (npm audit + Snyk) runs on every push, blocks on high-severity
  • Merge to <code>develop</code> auto-deploys to staging
  • Merge to <code>main</code> requires manual approval before production deploy
  • Database migrations run pre-deploy (<code>prisma migrate deploy</code>)
  • Rollback script available — <code>./scripts/rollback.sh</code>
  • Sentry release tagged on every production deploy
  • Slack notification on production deploy success/failure
  • Secrets stored in GitHub Secrets, never committed to repo
  • Container images tagged with git SHA for traceability
  • Smoke tests run after every deploy (health endpoints + critical paths)
