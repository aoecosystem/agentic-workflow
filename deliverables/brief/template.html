Style referenceThe chosen style maps to system-architecture/styles/<style>.md in the repo, which drives all downstream generation.
Architecture style — quick guide
  • monolith (default, recommended for <5 person teams): one app, one deploy, one database. Modules import each other directly. Fastest to ship, easiest to operate. Most projects start (and stay) here.
  • hybrid (recommended for ~70% of "we want microservices someday" projects): modular monolith with extraction-ready boundaries. One deploy + one DB today, BUT each service has strict interfaces (ports.ts) and owns its own tables (no cross-service FKs). Tomorrow you can lift any service out without rewriting business logic.
  • microservices (only when you have multiple teams + real distributed-system needs): independent services, DB per service, Kafka required, gateway in front. Real distributed-systems pain — pick this only when monolith / hybrid genuinely won't scale.
  • serverless (Lambda / Cloudflare Workers / Vercel Functions): pay-per-request, auto-scaling, stateless. Best for spiky traffic, JAMstack apps, edge-distributed APIs.

Pick what fits the project's scale and team — not what sounds impressive. You can change this later via /review-brief 3; downstream documents will need to be re-generated to pick up the change.

Rules for filling Section 6
  • 1-3 processes only. Critical flows only. Side flows (password reset, settings update) live under Section 5 features, not here.
  • Phase names are stable. Whatever you write here (SETUP, BOOKING, APPOINTMENT, etc.) is reused identically in the SoW Phase 5.5 Critical Flows and the Page Inventory — that's the universal join key.
  • Add roles as columns when needed. Two-role projects use ROLE_A + ROLE_B + SYSTEM. If your project has 3+ active roles in a process (e.g. CUSTOMER + PROVIDER + BUSINESS_OWNER + SYSTEM), add another column.
  • Always include SKIP and CANCEL alt rows when there's a meaningful failure path (no-show, manual cancel, refund, dispute). The agent uses these to design proper error handling.
  • Vertical variants are optional. Mention them only if your project has different business types sharing the same process with different rules.

13. Instructions for AI Agent

When this brief is sent to the AI, it should produce the adjusted Scope of Work following these rules.

AI Workflow
  1. Read this brief in full before starting
  2. Read the universal Scope-of-Work-Template.html for structure reference
  3. Replace all {{PLACEHOLDERS}} in the template with values from this brief
  4. Keep universal services S1–S6 intact (do not delete)
  5. Add project-specific services starting at S7 based on Section 5 features
  6. Generate new modules with naming convention SERVICE-MOD-NN
  7. Expand each Section 6 process into Phase 5.5 Critical Flows in the SoW — preserve phase names, then expand each phase into a full role × phase × system behavior matrix with timer values, state transitions, and per-vertical config (where applicable)
  8. Add new database tables with indexes for each new service
  9. Add new API endpoints to Phase 4
  10. Add new events to Phase 5 catalog
  11. Adjust Phase 6 tech stack with integrations from Section 7
  12. Generate Phase 7 Page Inventory last — every phase from Section 6 should map to at least one page
  13. Adjust Phase 8 module implementation order based on new dependencies
  14. Adjust Phase 10 risks/assumptions/out-of-scope from Sections 8 + 9
  15. Output as a new file: {{PROJECT_NAME}}-Scope-of-Work.html
  16. Do NOT modify the master template — always produce a new file

Quality Checklist

  • Every Feature ID maps to at least one API endpoint
  • Every System Behavior aligns with database schema and event catalog
  • Every new module has Rules + User Features + System Behaviors
  • Every Section 6 process has its phases in order with role × system actions; phase names are stable across the brief, the SoW Phase 5.5, and the Page Inventory
  • Every process has its phases in order with role × system actions; alt paths (SKIP / CANCEL) listed if applicable
  • Every database table has indexes defined
  • Naming conventions follow Glossary in template
  • No placeholder pills remain in final SoW (all replaced or marked as TBD)
